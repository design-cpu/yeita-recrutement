# deploy.sh ne vérifie pas la configuration résolue du service api avant de démarrer

## Résumé
L'API croit l'en-tête d'identité posé par oauth2-proxy : sa sécurité tient à ce qu'aucun port ne soit publié, qu'elle ne soit que sur le réseau interne `back`, et qu'aucune variable de mode local (`DEV_EMAIL`, `DEV_STATIC`) ne lui soit passée. Le `compose.yaml` du dépôt le garantit, et la QA l'a vérifié, mais `deploy.sh` ne le revérifie pas : un fichier `compose.override.yaml` ou un `COMPOSE_FILE` posé sur le serveur publierait l'API sans que le déploiement s'arrête. Un contrôle avant `up` fermerait cette porte.

## Priorité
**Moyenne** — conséquence grave si elle arrive (n'importe qui pourrait se faire passer pour un membre de l'équipe), mais il faut une erreur de configuration sur le serveur ; l'absence de contrôle est constatée dans `deploy.sh`, le risque n'a pas été provoqué.

## Détail
### Proposition
Dans `deploy/deploy.sh`, avant `docker compose up` (l. 109), lire `docker compose config --format json` et s'arrêter (sans rien toucher, message explicite) si `services.api.ports` n'est pas vide, si `services.api.networks` n'est pas exactement `{back}`, si `networks.back.internal` n'est pas `true`, ou si `services.api.environment` contient `DEV_EMAIL`, `DEV_STATIC`, `NODE_ENV` ou `HOST`. Essai dans le banc avec un `compose.override.yaml` qui publie `8000`.
### Bénéfice
Pour Yeita et les candidats : une erreur d'exploitation sur le serveur partagé ne peut pas exposer l'API ; pour la personne qui déploie : l'arrêt dit pourquoi.
### Existant à réutiliser
Lecture de `docker compose config` déjà faite par `deploy.sh` (l. 38, 56, 123) ; contrôles R22, R28 et R39 de la spec 1.3 (faits à la QA) ; fonction `arret`. Voir aussi 1.1-6 (contrôles des scripts de déploiement dupliqués, port et sous-réseau non revérifiés).
### Effort
S : un bloc `jq` (ou `node -e`) dans `deploy.sh`, un essai provoqué dans le banc.
