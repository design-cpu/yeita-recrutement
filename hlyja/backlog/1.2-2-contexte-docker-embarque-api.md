# Le contexte de construction Docker embarque api/, ses modules et une éventuelle base locale

## Résumé
L'image du site copie tout le dépôt (`COPY . .`) dans son étape de construction, et `.dockerignore` n'exclut pas le dossier `api/` arrivé en v1.2. Chaque construction envoie donc à Docker les 49 Mo de `api/node_modules`, et, sur un poste où l'API a tourné en local, la base `api/data/recrutement.sqlite` avec des dossiers de candidats. Le site publié n'en contient rien (`tools/build.py` écarte `api`), mais ces fichiers restent dans le cache de construction de la machine.

## Priorité
**Moyenne** — sans effet sur le site publié, mais des données personnelles peuvent se retrouver dans le cache de construction d'un poste, et le contexte grossit à chaque déploiement.

## Détail
### Constat
- `.dockerignore` : `.git`, `hlyja`, `_site`, `.env*`, `*.swp`, `*~` ; ni `api/node_modules` ni `api/data`.
- `docker/front.Dockerfile` l. 7 : `COPY . .` dans l'étape `build`, avant `tools/build.py`.
- `du -sh api/node_modules` : 49 Mo ; base par défaut `api/data/recrutement.sqlite` (`api/src/config.js` l. 11), ignorée par git (`.gitignore`) mais pas par Docker.
### Risque si on ne fait rien
Copie de la base locale d'un développeur dans une couche de cache ; contexte plus lourd et plus lent ; à la version qui construira l'image de l'API, risque d'y copier `node_modules` d'une autre plateforme (binaires de better-sqlite3).
### Piste
Ajouter `api/node_modules` et `api/data` (et les `*.sqlite*`) à `.dockerignore`, ou exclure `api/` du contexte de l'image du site et donner à l'API son propre contexte à la version qui la conteneurisera. Vérifier avec `docker build` que le site construit est identique.

## Traitement en 1.3
Fait : `.dockerignore` exclut `api/node_modules`, `api/data`, `**/*.sqlite`, `**/*.sqlite-wal`, `**/*.sqlite-shm` (revue de code 1.3, S4 : essai avec `api/y.sqlite` et `api/data/x.sqlite`, absents de l'image). L'image de l'API (`docker/api.Dockerfile`) installe ses modules elle-même (`npm ci --omit=dev`).
