# equipe.js pourrait refuser de tourner sous un autre utilisateur que le propriétaire de la base

## Résumé
Le premier administrateur est créé sur le serveur avec `node api/equipe.js add`. Lancée par `root` avant le premier démarrage de l'API, la commande crée la base et son dossier au nom de `root`, avec des droits fermés (600 et 700) : l'API, qui tourne sous un autre utilisateur, ne peut plus ouvrir sa base et refuse de démarrer. Le README demande d'utiliser le même utilisateur ; un refus explicite de `equipe.js` éviterait le piège.

## Priorité
**Basse** — l'échec est sûr et visible (l'API s'arrête en nommant la base), le README le prévient, et le cas n'a pas été essayé (QA : non essayé sans le serveur).

## Détail
### Proposition
Dans `api/equipe.js`, avant d'ouvrir la base : si le dossier de la base existe et que `process.getuid()` n'est pas son propriétaire, s'arrêter en code 1 (« Lance equipe.js avec l'utilisateur de l'API (<propriétaire>) ») ; si rien n'existe et que l'utilisateur est `root`, s'arrêter de même. Test avec un dossier d'un autre propriétaire (ou passage en `root` dans un conteneur).
### Bénéfice
Pour la personne qui installe l'API sur le serveur : pas de base au mauvais nom ni de `-wal`/`-shm` qui changent de propriétaire, pas de diagnostic à faire.
### Existant à réutiliser
Ligne « Base : <chemin absolu> » de chaque commande ; section « Première mise en place » d'`api/README.md` ; droits posés par `api/src/base.js` l. 53.
### Effort
S : un contrôle et un test.
