# deploy.sh lancé avec un masque 077 construit des images que l'API ne peut pas lire

## Résumé
`deploy/deploy.sh` ne fixe pas lui-même le masque des fichiers qu'il crée. Si la personne qui déploie a un shell réglé pour créer des fichiers privés (`umask 077`, ce que demandait la première version de la procédure des sauvegardes), `git pull` réécrit les fichiers modifiés en lecture pour leur seul propriétaire. Ces fichiers entrent tels quels dans les images, où l'API tourne sous un autre utilisateur (`node`) qui ne peut plus les lire : le déploiement casse l'API ou le site. La procédure des sauvegardes a été corrigée en 1.7, et la page de mise à jour (`deploy/METTRE-A-JOUR.md`) lance désormais `umask 022 && … deploy/deploy.sh` ; mais le script lui-même reste exposé, et `deploy/README.md` § 9 le lance encore sans ce masque.

## Priorité
**Haute** — bug majeur sur le parcours de déploiement, reproduit (fichier en 600, puis `EACCES` dans l'image api : l'API ne démarre pas) ; le déclencheur (un shell à `umask 077`) est devenu rare depuis la correction de `deploy/README.md` § 14, mais une ligne `umask 022` dans `deploy.sh` suffit à l'écarter. Revue à la reprise (2026-10-28) : inchangée ; le contournement de `METTRE-A-JOUR.md` ne protège que qui suit cette page.

## Détail
### Reproduire
Dans un dossier temporaire hors du dépôt, sans rien modifier dans le projet :
```bash
d=$(mktemp -d /private/tmp/claude-501/-Users-sderrouazi-Documents-Yeita-Projects-Github-yeita-recrutement/207d9144-6686-4cbe-bd9a-74cfcb051f91/scratchpad/repro-umask.XXXXXX)
git clone -q /Users/sderrouazi/Documents/Yeita/Projects/Github/yeita-recrutement "$d/r" && cd "$d/r"
rm api/server.js && (umask 077 && git checkout -- api/server.js)   # comme un git pull qui réécrit ce fichier
stat -f '%Lp %N' api/server.js                                      # attendu : 600
docker build -q -f docker/api.Dockerfile -t repro-umask-api .
docker run --rm repro-umask-api node -e "require('fs').readFileSync('/app/api/server.js'); console.log('lisible')"
docker rmi repro-umask-api; rm -rf "$d"
```
### Attendu
Le fichier reste lisible par `node` dans l'image (« lisible »), quel que soit le masque du shell qui lance `deploy.sh`.
### Observé
Constaté à la lecture (non exécuté) : git crée les fichiers avec `0666 & ~umask` (600 sous `umask 077`) ; `docker/api.Dockerfile` copie `api/` en root (`COPY api/ ./`) puis passe en `USER node` ; un fichier 600 de root est illisible par `node` (attendu : `EACCES`, l'API ne démarre pas). Même risque pour l'image du site (`docker/front.Dockerfile`, `COPY . .` puis service par oauth2-proxy, utilisateur non root).
### Où
`deploy/deploy.sh` (`main`, avant `git checkout` / `git pull`, l. 95-99) : ajouter `umask 022`. `deploy.sh` était exclu de la 1.7 (spec finale, Exclu : « modification de `deploy/deploy.sh` »). Une fois corrigé, retirer le `umask 022 &&` de `deploy/METTRE-A-JOUR.md` § 2 (l. 23-26) ou le garder comme double sécurité, et aligner `deploy/README.md` § 9.
### Preuve
`reproduite` (2026-10-27, orchestrateur, dossier temporaire du scratchpad, rien dans le dépôt) : `stat` → `600 api/server.js` ; `docker run … readFileSync('/app/api/server.js')` → `Error: EACCES: permission denied, open '/app/api/server.js'`.
