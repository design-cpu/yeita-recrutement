# Décisions techniques

> Les choix d'architecture qui orientent le dépôt, avec ce qu'ils écartent. Une décision remplacée reste listée.
> v1.1 : hébergement Docker sur le serveur OVH derrière oauth2-proxy ; `reverse_proxy = false`.
> v1.2 : API de stockage Node.js sur SQLite, qui croit `X-Forwarded-Email` et n'écoute que sur 127.0.0.1 par défaut ; version optimiste ; effacement réel et journal purgé à la suppression.
> v1.9 : déploiement automatique par le serveur ; l'application dépose une demande, l'hôte décide sur ses propres fichiers ; demandes limitées à la ligne principale de `main` ; retour par le `deploy.sh` du commit d'avant.
> v1.3 : pages branchées sur l'API (mode serveur, jamais de repli silencieux en production), réseau `back` sans adresse hôte, image Node figée, fiches qui écrivent leur partie, « Remplacer tout » masqué en mode serveur.

| Confiance dans `X-Forwarded-Email` | oauth2-proxy v7.15.5 retire un en-tête forgé (route publique ou protégée), mais un accès direct à l'API le laisse passer (vérifié, v1.2) | L'API croit l'en-tête, vérifie l'équipe à chaque requête ; écoute sur `127.0.0.1` par défaut, `HOST` pour la changer, avertissement sinon ; mode local (`DEV_EMAIL`, `DEV_STATIC`) refusé hors bouclage ou en production (choix de l'utilisateur pour `HOST`) | Écoute sur toutes les interfaces ; secret partagé entre proxy et API | Le port de l'API ne doit jamais être publié hors du réseau d'oauth2-proxy ; avec Google, l'email posé reste à vérifier (H1) | 1.2 |
| Conflits par version optimiste | Deux recruteurs écrivent le même dossier | Colonne `version` ; PUT `version: null` = création ; sinon mise à jour si la version lue est la bonne ; tout autre cas (version périmée, id existant, dossier supprimé) → 409 « La candidature a été modifiée par quelqu'un d'autre. Recharge la page. » | Dernier écrit gagne ; 404 pour un dossier supprimé | L'adaptateur garde la version de l'enveloppe par id, distincte de `data.version` | 1.2 |
| Effacement réel | Un `DELETE` SQLite laisse le contenu lisible dans les fichiers (vérifié, v1.2) | `secure_delete = ON` et `wal_checkpoint(TRUNCATE)` après chaque écriture sur `candidats` (PUT, DELETE) ; à la suppression, journal du dossier purgé, une ligne `suppression` gardée (choix de l'utilisateur) | Garder tout le journal ; point de contrôle automatique seul | Un lecteur ouvert (sauvegarde, `sqlite3`) peut retarder l'effacement jusqu'à l'écriture suivante (avertissement journalisé) | 1.2 |
| Dépendances de moins de 14 jours | Fastify 5.12.5 a une faille faible ; ses correctifs et 9 dépendances transitives ont moins de 14 jours | Fastify 5.12.7 et lockfile gardé tel quel, exception notée (choix de l'utilisateur) | Versions de plus de 14 jours : 4 failles modérées de fast-uri | `npm audit` : 0 vulnérabilité au 26 octobre 2026 | 1.2 |
| Choix du mode des pages | À la lettre, le pitch passait en mode navigateur dès que `/api/moi` ne rendait pas 200 ; une API arrêtée (502) ou une session expirée (401) auraient fait écrire les recruteurs en silence dans leur navigateur, en production (vérifié, v1.3, V9, V10) | Mode navigateur sur 404 seul, hors de l'hôte de `YEITA.SITE`, ou en `file://` ; 401 → un rechargement (garde de 60 s contre la boucle) ; tout le reste → mode bloqué avec un bandeau, rien n'est lu ni écrit (décisions de l'utilisateur, v1.3) | Tout échec → mode navigateur (lettre du pitch) | Un oauth2-proxy mal réglé en production bloque les pages au lieu de les faire basculer ; les tests et les aperçus statiques restent en mode navigateur | 1.3 |
| Versions et file par dossier | Les pages enregistrent toutes les 300 à 400 ms sans attendre le précédent, et certaines gardent un dossier lu à l'ouverture | Version retenue par objet dossier (`WeakMap`) et, à défaut, la plus haute par identifiant ; requêtes d'un même dossier en file ; aucune nouvelle tentative par l'adaptateur | Version par identifiant seul (un objet ancien écraserait une version récente) ; « dernier écrit gagne » | Un recruteur seul ne se met pas en conflit avec lui-même ; un conflit réel est refusé et affiché | 1.3 |
| Fiches qui écrivent leur partie | La fiche EC1 et la feuille de décompte d'un même candidat sont faites pour être ouvertes ensemble ; chacune écrivait le dossier entier lu à l'ouverture | `DOSSIER.ecrirePartie` : relire, comparer sa partie à la dernière lue ou écrite, la poser, écrire ; refus si elle a changé ailleurs ou si le dossier a disparu ; départ de la page : partie posée sur l'objet du PUT en cours ou le dernier relu, avec sa version (revue v1.3, Q1) | Recopier tout le dossier (refus mutuel, puis écrasement) | Les deux modes ; perte possible des 300 à 400 dernières ms au départ de la page si quelqu'un a écrit entre-temps (risque accepté, H5) | 1.3 |
| Réseau `back` sans adresse hôte | Sur un moteur Linux, l'hôte et tout conteneur en réseau hôte joignent un conteneur d'un réseau `internal` par son adresse, en IPv4 et en IPv6 si actif ; l'API croit `X-Forwarded-Email` (vérifié, v1.3, V30, V39) | `internal: true`, `enable_ipv6: false`, `com.docker.network.bridge.inhibit_ipv4: "true"` ; aucun port publié ; contrôle réseau avant le premier admin (`deploy/README.md` § 9b) | `gateway_mode_ipv4: isolated` (même effet, option plus récente) ; secret partagé proxy/API (évolution de l'API, hors périmètre) | Vérifié sur le moteur 29.9.2 ; à refaire sur un moteur plus ancien | 1.3 |
| Image Node figée | `node:22-slim` = 22.23.4, correctif de sécurité de moins de 14 jours | `node:22.23.4-slim` figée par le digest de l'index multi-architecture (choix de l'utilisateur, exception à l'âge minimal) | `node:22-slim` flottante ; 22.23.3 (plus de 14 jours, sans le correctif) | Mise à jour par changement explicite du digest | 1.3 |
| Fichiers des candidats dans SQLite | CV et portfolio déposés depuis la fiche du candidat (1.10), à garder dans le stockage sécurisé, avec la même durée et le même effacement que le dossier | Table `fichiers` dans la base existante (BLOB), routes sous `/api/candidats/:id/fichiers`, sans dépendance nouvelle (analyseur Fastify encapsulé), 10 Mo, PDF/PNG/JPG vérifiés aux premiers octets (validé par l'utilisateur, 27 octobre 2026) | Dossier de fichiers sur un volume ; `@fastify/multipart` ; fichiers dans le JSON du dossier (limite de 1 Mo, et chaque enregistrement les renverrait) | Même accès, même `secure_delete`, même sauvegarde que les dossiers ; la base grossit avec les documents ; un nginx devant le site doit accepter 10 Mo | 1.10 |
| « Remplacer tout » masqué en mode serveur | En mode serveur, l'import « Remplacer tout » supprimerait les dossiers de toute l'équipe absents du fichier, sans sauvegarde | Seule la fusion est proposée en mode serveur (choix de l'utilisateur) ; `store.js` inchangé | Garder l'option avec un avertissement | Un import « Fusion » d'un vieil export peut recréer un dossier supprimé (écrit dans `MODELE.md`) | 1.3 |
| Méthode de copie | Une lecture longue de la base empêche le point de contrôle de l'API, et un dossier supprimé reste lisible jusqu'à l'enregistrement suivant (fiche 1.2-5) | `db.backup()` de better-sqlite3 dans le conteneur (`api/sauvegarde.js`), contrôle `integrity_check`, un seul fichier (`journal_mode = DELETE`), sous un nom temporaire puis renommé (décision du pitch) | `sqlite3 .backup`, copie des fichiers à chaud, `VACUUM INTO` | Aucune lecture gardée au-delà de la copie ; sans `journal_mode = DELETE`, la copie garderait l'en-tête WAL de la base et créerait `-wal`/`-shm` à son ouverture (vérifié, v1.7) | 1.7 |
| Chiffrement et clé | Les copies contiennent les dossiers candidat | `age` vers une seule clé publique `age1…` (`AGE_RECIPIENT`) ; clé privée créée sur un Mac, jamais sur le serveur ; pour l'instant un fichier `.txt` gardé et partagé en main propre par l'utilisateur (coffre interne plus tard, `deploy/CLE-SAUVEGARDE.md`) ; déchiffrement sur un Mac seulement (décisions du pitch et de l'utilisateur) | GPG ; clé SSH comme destinataire (age l'accepte : refusée par `backup.sh`) ; retirer le chiffrement (décision de l'utilisateur : gardé) | Perte du fichier = copies illisibles ; contrôle par déchiffrement après la première sauvegarde | 1.7 |
| Copies sur le serveur seulement | OVH Object Storage est payant ; aucun autre stockage gratuit retenu | Copies chiffrées gardées 30 jours dans `/var/backups/recrutement`, sur le serveur (décision de l'utilisateur, reprise du 2026-10-28) | OVH Object Storage, rclone et le client `aws` (retirés) ; Google Drive de Workspace (proposé, non retenu) | La perte du serveur emporte les sauvegardes (accepté) ; durée maximale d'un dossier supprimé dans les copies : 3 j (volume), 31 j (serveur) | 1.7 |
| Page d'état au lieu d'alertes | Savoir si les sauvegardes tournent, sans service tiers | État écrit par les scripts dans le volume (`/data/etat`), lu par `GET /api/sauvegardes` (rôle `admin`), affiché par `admin/sauvegardes.html` (vert, ou rouge avec motifs) ; `/admin/` réservé au futur tableau de bord (décisions de l'utilisateur) | healthchecks.io (retiré) ; lien depuis Candidatures (refusé par l'utilisateur) ; `/dashboard/` (nom anglais, remplacé par `/admin/`) | Aucune alerte envoyée : vérification à la main ; emails dans une évolution ultérieure | 1.7 |
| Restauration | La copie en clair ne doit jamais toucher le disque du serveur ; une restauration ratée ne doit pas détruire la base | Copie envoyée par l'entrée standard de `docker compose run` dans le volume, en tant que `node` ; empreinte SHA-256 et `integrity_check` vérifiés dans le conteneur avant de remplacer ; état actuel sauvegardé avant ; suppressions refaites dans l'interface | `docker compose cp` vers le volume (fichier posé à l'uid de `deploy`, illisible par l'api, vérifié v1.7) ; réécrire les suppressions en SQL hors de l'API | `deploy/RESTAURER.md` rejoué sur le banc (3 cas) | 1.7 |
| Déploiement automatique sans GitHub Actions (v1.9) | Mettre `main` en ligne sans SSH, après les tests, sans service tiers | Le serveur vérifie lui-même : timer systemd de 10 min et unité path sur la demande, `deploy/auto-deploy.sh` en tant que `deploy` ; tests dans un worktree temporaire et des conteneurs jetables (image Node du `FROM` de `docker/api.Dockerfile`), construction sous des noms d'image d'essai (`compose.yaml` fixe les noms : sans surcharge, l'essai écraserait les images en ligne) | GitHub Actions et préproduction (hors pitch) ; Node sur l'hôte (non installé) ; jq ou python pour le JSON (pas garantis : le shell échappe, `iconv -c`) | Un passage dure de 35 s (cache) à quelques minutes ; le cache de construction reste (surveillé par `verif-disque`) | 1.9 |
| Frontière application → hôte (v1.9) | La page doit pouvoir demander un déploiement sans piloter l'hôte | L'API ne fait que déposer `demandes/deploiement.demande` (clé=valeur) dans son volume ; l'hôte la prend par un conteneur jetable (il ne lit jamais le volume depuis l'hôte), la lit strictement et valide le commit ; ses décisions (`deploye`, `echec`, `incertain`, `retour-ko`, `en-cours`, passages) sont dans `~deploy/.recrutement-deploiement/`, jamais dans le volume ; `deploiement.json` n'est qu'une vue | Point de montage partagé avec l'hôte (changerait `compose.yaml`, mêlerait les droits de `node` et `deploy`) ; décisions relues dans `deploiement.json` (l'application pourrait les falsifier) | L'application compromise ne peut que déployer un commit testé de la ligne principale ≥ 1.9, poser ou retirer la pause, faire tourner le service : une demande illisible est retirée et enregistrée « refusée » (elle peut remplir les 30 passages de la page ; le journal fait foi), une demande qu'elle empêche de retirer (dossier remplacé, conteneur en échec) ne fait tourner le service qu'une fois par minute, sans rien enregistrer | 1.9 |
| Commits admis depuis la page (v1.9) | Le dépôt fusionne par merge : 227 ancêtres de `main` pour 19 commits sur la ligne principale | `git rev-list --first-parent origin/main` (décision de l'utilisateur, 2026-10-28) et présence de `deploy/auto-deploy.sh` (décision de l'utilisateur) ; `deploy.sh <hash>` en SSH garde « ancêtre de main » | Tout ancêtre (commits intermédiaires jamais relus ni mis en ligne) | Une étape d'une branche ne peut être mise en ligne qu'en SSH | 1.9 |
| Retour automatique et pause (v1.9) | Un `deploy.sh` raté laisse le dépôt sur le nouveau commit ; un retour manuel ne doit pas être défait | Retour automatique au commit d'avant (décision de l'utilisateur), par le `deploy.sh` **de ce commit-là**, extrait sous le verrou ; arrêt avant changement (pas de `· Dépôt sur`) sans retour ; pause `deploy/PAUSE` posée par celui qui demande un commit précis (page, ou `deploy.sh` à la main), jamais par l'automatisme (`RECRUTEMENT_PAR_AUTO=1`) ; un déploiement fait à la main pendant les tests l'emporte (`annule`) | Retour par le `deploy.sh` du commit en échec (cassé avec lui) ; pause décidée par `deploy.sh` d'après son propre `fetch` (`main` qui avance pendant les tests aurait mis en pause) ; `.gitignore` pour `PAUSE` (perdu en revenant à un ancien commit : exclusion locale `.git/info/exclude`) | Le pire cas (retour raté, passage tué pendant la mise en ligne) est une alerte rouge sur la page avec la commande à lancer ; aucune notification (hors pitch) | 1.9 |
