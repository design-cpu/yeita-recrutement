# Étonnements — version 1.8

> Un script qui se remplace en tournant doit être spécifié et testé commande par commande selon la version du script qui tourne vraiment, et une faille de procédure de production trouvée en revue se corrige dans la page lue sur le serveur avant la QA, même classée mineure.

## 1. Un script qui se met à jour ne profite pas de sa propre correction
**Ce qui s'est passé** : la spec v1 de la 1.8 ne disait pas sur quel commit partait le banc ni pourquoi garder `umask 022 &&` ; la revue de spec (T1, T2) a rappelé que bash exécute le `deploy.sh` du disque, lu avant le `git pull` : la correction ne protège ni le premier passage à la 1.8 ni une commande lancée après un retour vers un commit d'avant. La revue de code (constat 1) a trouvé un troisième cas (échec d'un retour vers un commit d'avant la 1.8), que la QA a confirmé et qui a dû être ajouté après coup à `deploy/METTRE-A-JOUR.md` § 4.
**Ce que j'en retiens** : pour un script qui change de version en cours d'exécution, la question « quelle version du script tourne à ce moment ? » se pose pour chaque commande documentée, pas seulement pour la mise à jour normale.
**Règle pour la suite** : Quand une version corrige un script qui remplace ses propres fichiers en s'exécutant (déploiement, mise à jour, retour arrière), la spec v1 contient un tableau qui donne, pour chaque commande documentée qui le lance (mise à jour, premier passage à la version, retour vers une version antérieure, commande affichée après un échec, dans les deux sens), la version du script qui tourne et la protection qui s'applique ; la QA part d'un dépôt qui contient déjà la correction et rejoue au moins une ligne où l'ancien script tourne.

## 2. Une exception de procédure de production laissée en mineur non traité
**Ce qui s'est passé** : la revue de code (constat 1, « mineur », « non traité ») a montré que R5 était faux pour un cas réel : après l'échec d'un retour vers un commit d'avant la 1.8, la commande de retour affichée réécrit les fichiers en 600. `deploy/METTRE-A-JOUR.md`, la page qu'on lit sur le serveur, n'en disait rien ; seule la vue humaine `mise-a-jour-production.humain.md` l'a écrit. La QA l'a relevé hors CA (`qa/rapport-qa.md`, « À vérifier à la main ») et l'exception a été ajoutée après la QA, donc sans être rejouée par elle.
**Ce que j'en retiens** : en mode standard, « mineur non traité » laisse passer une consigne fausse dans une procédure d'urgence ; ce n'est pas la gravité du code, c'est celle de la consigne.
**Règle pour la suite** : En mode standard, un constat de revue de code, même mineur, qui montre qu'une règle de la spec est fausse ou qu'une procédure à suivre en production (commande à lancer, exception, ordre des gestes) est incomplète est corrigé avant la QA dans la page de procédure lue sur le serveur et dans sa source `technique/`, et la QA rejoue le cas décrit.
