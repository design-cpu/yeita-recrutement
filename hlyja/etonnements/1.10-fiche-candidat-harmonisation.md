# Étonnements — version 1.10

> Une branche reprise dont tous les tests passent peut quand même casser ce que main a ajouté depuis : la faire tourner avec le code de main est ce qui l'a montré ; et les gestes mécaniques (suppression par motif, arrêt par port) ont fait les deux dégâts de la version.

## 1. Reprendre une branche née avant des versions de main : rejouer le code de main sur ses données
**Ce qui s'est passé** : la branche de Léo, écrite avant les versions 1.7 à 1.9 de main, passait la base en `user_version` 2 ; ses tests passaient tous après le rejeu, mais l'API de la 1.9 refusait la base migrée, ce qui cassait le retour automatique du déploiement apparu en 1.9 (V4). La procédure de restauration (1.7) aurait aussi cassé si la table avait été comptée sans précaution (O2, tour 1).
**Ce que j'en retiens** : rejouer une branche et voir ses tests au vert ne dit rien de sa compatibilité avec les mécanismes ajoutés à main depuis sa base ; seuls les faire tourner avec les données de la branche le montre.
**Règle pour la suite** : Quand une version reprend une branche dont la base est antérieure à des versions de main, le cadrage liste les mécanismes ajoutés à main depuis cette base (`git log <base>..main`), et avant la spec v1 les vérifications font tourner le code de main sur des données produites par la branche (ouverture de la base par l'ancienne version, retour arrière, restauration d'une copie), résultat noté avec un identifiant V.

## 2. Une suppression par motif dans un fichier partagé a cassé une règle voisine
**Ce qui s'est passé** : en retirant du CSS mort par expression régulière, la ligne `details.liens-fiche{…}` a perdu sa fin et « details » s'est collé au sélecteur suivant : `.carte-h` est devenu `details.carte-h`, l'en-tête de la carte d'identité était cassé ; aucun test ne l'a vu, la revérification de la revue de code l'a trouvé (N1).
**Ce que j'en retiens** : une suppression mécanique se relit sur le diff ligne à ligne ; une ligne modifiée au lieu d'être supprimée signale qu'elle a mordu sur autre chose.
**Règle pour la suite** : Après toute suppression faite par script ou par expression régulière, l'orchestrateur relit `git diff -U0` du fichier et n'accepte que des lignes entièrement supprimées ; toute ligne `+` non voulue est corrigée avant le commit, et un contrôle de rendu (style calculé) est ajouté pour le composant voisin touché.

## 3. Ne jamais arrêter un processus par son port sur le poste
**Ce qui s'est passé** : pour arrêter l'API de banc, `lsof -ti tcp:18800 | xargs kill` a aussi tué Docker Desktop, qui relayait ce port vers un conteneur ; Docker a dû être relancé, deux conteneurs de banc de l'utilisateur sont restés arrêtés (incident noté sous V9).
**Ce que j'en retiens** : sur macOS, un port relayé par Docker appartient au processus de Docker Desktop.
**Règle pour la suite** : Un processus lancé pour un essai est arrêté par le PID noté à son lancement, ou par le nom de son conteneur, jamais par son port ; les consignes données aux sous-agents qui lancent des bancs le rappellent.

## 4. Un test dit « instable » par une source est rejoué avant d'accepter le mot
**Ce qui s'est passé** : la description de la branche disait qu'un contrôle e2e échouait « par intermittence aussi sur main » ; les vérifications l'ont d'abord accepté (V3) ; rejoué 3 fois sur main et à chaque passage sur la branche, il échouait toujours, avec le message du bug connu 1.9-1 (V21, revue du backlog).
**Ce que j'en retiens** : « instable » est une hypothèse ; le message d'échec comparé aux fiches du backlog dit souvent ce que c'est.
**Règle pour la suite** : Avant que la spec ou le bilan admettent un contrôle qu'une source qualifie d'instable ou de préexistant, ce contrôle est rejoué au moins trois fois sur la branche principale et sur la branche de la version, et son message d'échec est comparé aux fiches ouvertes du backlog ; le résultat est noté avec un identifiant V.

## 5. Mutations : une survivante peut révéler du code inutile (fusion avec la règle 4 de la 1.9)
**Ce qui s'est passé** : la mutation T5 (enregistrements différés qui n'attendent plus la fin d'un dépôt) a survécu ; la file par dossier de l'adaptateur garantissait déjà l'ordre : le garde-fou a été retiré (`7e11deb`, fiche de la tâche 03).
**Ce que j'en retiens** : face à une survivante, se demander d'abord si le comportement visé est observable.
**Règle pour la suite** : L'outil de mutation lance la suite avec une durée maximale par test (`--test-timeout` ou équivalent) et classe chaque mutation selon la conclusion de la suite, jamais selon la seule présence de lignes FAIL : « détectée » (échec avec le message de l'assertion visée), « survivante » (suite conclue sans échec), « bloque » (durée maximale dépassée) ou « plantage » (arrêt sans conclusion : exception, rejet non traité, code de sortie anormal) ; tout test qui lance un processus, ouvre un port ou attend un verrou enregistre l'arrêt de ce qu'il lance dès sa création (`t.after`, `finally`) et a sa propre échéance, plus courte, qui échoue avec un message d'assertion ; une suite asynchrone transforme tout rejet non traité en échec consigné et continue ; une mutation « bloque » ou « plantage » est notée comme telle dans la section Mutations, sa cause analysée et le test corrigé jusqu'à ce qu'elle échoue avec le message de l'assertion visée ; pour chaque mutation « survivante », la fiche dit d'abord si le comportement visé est observable : si un autre contrôle masque celui qu'elle vise, on ajoute le cas que seul le contrôle visé arrête, jamais en retirant ou en fusionnant l'un des deux contrôles ; si le comportement est observable, un test est ajouté ; s'il ne l'est pas parce qu'un autre mécanisme le garantit déjà, la fiche nomme ce mécanisme et le test qui le couvre, le code muté est retiré avec cette raison dans le commit et la fiche, et la revue de code vérifie que ce test existe (un contrôle de sécurité, de validation ou de garde n'est jamais retiré à ce titre) ; une assertion « rien n'a été ajouté » ou « un élément a été ajouté » sur une liste à rétention bornée compare l'identifiant du dernier élément, jamais le nombre d'éléments.

Règles récurrentes :
- Un contrôle compté sans pouvoir échouer, ou une survivante mal traitée : septième occurrence (1.2, 1.3, 1.4, 1.7, 1.9, 1.10). Le skill (`controles.md` § 6) devrait porter les quatre issues et l'arbre « masquée / observable / garantie ailleurs » au lieu d'une nouvelle fusion par version.
- Une vérification faite dans des conditions plus favorables que la réalité : septième version (1.1, 1.2, 1.3, 1.4, 1.7, 1.9, 1.10). `controles.md` § 1 devrait avoir la colonne « conditions » et exiger de vérifier toute affirmation reprise d'une source (description de branche, fiche) sur un échec ou une compatibilité.
- Retour arrière vers la version précédente non essayé avant la spec : deuxième occurrence (1.8 pour le script, 1.10 pour les données). Le template de spec pourrait imposer une ligne « retour vers la version précédente » (script et données) dès qu'une version touche au déploiement ou au schéma.
